# IMA 知识库 PDF 鱼类书籍读取问题讨论

## 1. 问题背景

dsh-aquasense 插件的知识库模块依赖 IMA（腾讯文档智能助手）API 查询鱼类养殖参考资料。当前 IMA 知识库中存放了 84 个 PDF 文件（含《鲈鱼养殖手册》《水产疾病防治》等专业书籍）以及若干用户笔记。

**核心矛盾**: IMA 的开放 API 只能读取**笔记（note）**的正文内容，无法直接读取 PDF 文件的正文。而笔记是 IMA 平台 AI 对原始资料的**二次汇总**，并非最原始的参考资料本身。

这意味着：我们用来生成处置建议的"原文引用"，其信息源头是 AI 汇总后的笔记，而非鱼类养殖书籍的原始段落。信息经过了 IMA 平台 AI 的压缩、改写和筛选，存在信息损失与失真的风险。

然而，调研发现 IMA 平台**内部**其实具备强大的 PDF 解析能力——包括图片提取、章节定位、原文跳转等——只是这些能力尚未通过开放 API 完整暴露。

## 2. IMA 平台内部 PDF 解析机制（调研发现）

### 2.1 IMA 客户端的 PDF 处理能力

IMA 在客户端/UI 层面具备完整的 PDF 智能解析能力，远超开放 API 所暴露的功能：

```
用户上传 PDF
    │
    ▼
┌─────────────────────────────────────────────────┐
│ IMA 内部 PDF 解析 Pipeline                        │
│                                                   │
│ 1. 文本提取                                       │
│    ├─ 原生 PDF: 直接提取文本对象(保留坐标/页码)     │
│    ├─ 扫描件: OCR 识别(PaddleOCR/Tesseract)       │
│    └─ 混合型: 文本层+OCR 补充                      │
│                                                   │
│ 2. 图片提取                                       │
│    ├─ 矢量图: 提取元数据/Alt Text/对象ID           │
│    ├─ 光栅图(JPG/PNG): 提取嵌入图像               │
│    └─ 图表: 识别坐标轴/图例/数据点 → 结构化数据    │
│                                                   │
│ 3. 版面分析                                       │
│    ├─ 识别: 标题/正文/表格/图片/页眉页脚            │
│    ├─ 多栏排版还原                                 │
│    └─ 图文混排关联(图片↔配图标题↔正文引用)         │
│                                                   │
│ 4. 结构化切片                                     │
│    ├─ 按语义分块(512-1024 tokens/块)              │
│    ├─ 保留: 页码/章节/段落位置元数据               │
│    └─ 保留: 图片引用关系(图→标题→上下文)           │
│                                                   │
│ 5. 向量化索引                                     │
│    ├─ 文本: Sentence-BERT → 768维向量              │
│    ├─ 图片: CLIP → 视觉向量(与文本统一空间)        │
│    └─ 知识图谱: 自动构建知识点间关联               │
└─────────────────────────────────────────────────┘
```

### 2.2 IMA 客户端可做但 API 不暴露的能力

| 能力 | 客户端/UI | OpenAPI | 说明 |
|------|:---------:|:-------:|------|
| PDF 全文语义搜索 | ✅ | ❌ | 客户端可搜 PDF 正文，API 的 `search_knowledge` 仅搜标题 |
| 原文段落定位(页码/章节) | ✅ | ❌ | 客户端引用带页码锚点，点击可跳转到 PDF 对应位置 |
| PDF 内嵌图片引用 | ✅ | ❌ | 客户端可展示 PDF 中的图表/配图，并关联到正文上下文 |
| 图表数据提取 | ✅ | ❌ | 柱状图/折线图/饼图可被识别并转化为结构化数据 |
| 章节级定位 | ✅ | ❌ | 问"第三章讲了什么"可精确定位到对应章节 |
| 跨文档对比 | ✅ | ❌ | 多文档间的交叉引用和对比分析 |
| 划词追问 | ✅ | ❌ | 选中 PDF 段落 → AI 解读该段上下文 |
| 原文溯源跳转 | ✅ | ❌ | 回答中的引用编号可点击跳转到 PDF 原文位置 |

### 2.4 核心差距:API 暴露 vs 平台能力

```
IMA 平台内部能力:
  PDF → 版面分析 → 结构化切片(含页码/章节/图片) → 向量索引
                                                         ↓
  客户端: 语义搜索 → 原文定位(页码+章节) → 图片引用 → 跳转

OpenAPI 暴露的能力:
  search_knowledge: 仅搜标题 → 命中文件名
  get_media_info: 返回 url_info(下载链接) → 下载原始 PDF
  get_doc_content: 仅笔记可用 → 读笔记文本

  缺失: PDF 正文搜索 / 页码定位 / 图片提取 / 章节元数据
```

**这意味着**: IMA 已经为每个 PDF 建立了包含页码、章节、图片位置的结构化索引，但这些元数据没有通过 OpenAPI 暴露给第三方开发者。我们只能拿到原始 PDF 的下载链接，自行解析。

## 3. 当前架构分析

### 3.1 双通道检索现状

当前系统采用**双通道互补**设计：

```
通道 A: searchKnowledge (wiki/v1/search_knowledge)
  - 索引范围: 仅文件名/文件夹名
  - 问题: 搜索"氨氮"无法命中 PDF 正文中的"氨氮超标处理方案"
  - 用途: 定位文件条目(书名级匹配)

通道 B: searchNote (note/v1/search_note)
  - 索引范围: 笔记正文全文
  - 优势: 能命中正文关键词,回带高亮原文
  - 问题: 笔记是 AI 二次汇总,非原始 PDF 内容
```

### 3.2 正文读取路径

| 媒体类型 | media_type | 正文读取方式 | 内容质量 |
|----------|------------|-------------|---------|
| PDF | 1 | 下载 → unpdf(pdf.js)提取文本层 → 缓存 | **原始内容**，但只能通过 `getMediaInfo` 的 `url_info` 下载 |
| 笔记 | 11 | `note/v1/get_doc_content` 读纯文本 → 缓存 | **AI 二次汇总**，非原始参考资料 |
| 其他 | - | 字段提取 + 占位标记 | 不可靠 |

### 3.3 关键 API 能力对比

```
IMA 开放 API 能力矩阵:

┌─────────────────────────────┬────────────┬────────────┐
│ 操作                         │ PDF(1)     │ 笔记(11)   │
├─────────────────────────────┼────────────┼────────────┤
│ 按名称搜索(searchKnowledge)  │ ✅ 仅标题  │ ✅ 仅标题   │
│ 按正文搜索(searchNote)       │ ❌ 不索引  │ ✅ 全文索引 │
│ 下载/读取正文                │ ✅ url下载 │ ✅ API直读  │
│ 获取结构化内容               │ ⚠️ 纯文本 │ ⚠️ 纯文本  │
└─────────────────────────────┴────────────┴────────────┘
```

## 4. 问题详解:笔记 ≠ 原始 PDF

### 4.1 笔记的本质

IMA 笔记是用户在 IMA 平台中创建的文档，通常是对 PDF 书籍的**阅读笔记、摘要、摘录**。它们的特征：

- **信息密度降低**: 原书一个章节可能被压缩为几段摘要
- **选择性汇总**: IMA AI 会根据"重要性"筛选内容，可能遗漏原始资料中的关键细节
- **语义改写**: 原文的专业术语和精确表述可能被简化或替换
- **上下文丢失**: 原书中图表、公式、实验数据等非文本信息无法通过笔记体现
- **时效性不确定**: 笔记创建时间未知，可能基于旧版 PDF 内容

### 4.2 对处置建议质量的影响

当前 `aquasense_advice` 工具的三段式输出依赖知识库原文引用：

```
① 原文引用 (knowledge_excerpt)
   《鲈鱼养殖技术》:「白点病由小瓜虫引起,水温15-25℃高发...」
   ↑ 这段"原文"实际来自笔记,可能遗漏了原书中关于
     小瓜虫生活史、不同鲈鱼品种易感性差异等关键信息

② 逻辑推理 (reasoning)
   "症状「白点、蹭壁」在知识库《鲈鱼养殖技术》中定位到相关原文"
   ↑ 推理基于的信息源是二次汇总,置信度应低于原始文献

③ 总结 (diagnosis_summary + 处置建议)
   ↑ 最终建议的信息链条: 原始PDF → IMA AI汇总 → 笔记 → 搜索命中 → 摘录 → 建议
   信息经过多次转译,每一步都可能引入偏差
```

### 4.3 典型场景举例

**场景**: 鲈鱼出现"白点 + 蹭壁"症状

| 信息源 | 可能的内容 | 信息完整度 |
|--------|-----------|-----------|
| 原始 PDF《鲈鱼病害防治》 | "白点病(小瓜虫病):病原为多子小瓜虫,适宜水温15-28℃...治疗:①福尔马林 25ppm 药浴 ②亚甲基蓝 2ppm 全池泼洒 ③提高水温至30℃以上...注意事项:鲈鱼对有机磷敏感,禁用敌百虫..." | 100% |
| IMA 笔记(二次汇总) | "白点病:小瓜虫引起,可用福尔马林或亚甲基蓝治疗,注意升温" | ~30% |
| 系统实际引用 | "白点病由小瓜虫引起...福尔马林药浴..." | ~20%(笔记摘录截断) |

笔记版本遗漏了：
- 具体浓度和用法
- 鲈鱼对有机磷的特殊敏感性（关键安全信息）
- 多种治疗方案的比较和选择依据
- 禁忌症和药物配伍

## 5. 现有缓解措施及其局限

### 5.1 PDF 直接下载解析（已实现）

系统已实现 PDF 正文提取路径：`getMediaContent(mediaId)` → `getMediaInfo` → `url_info` 下载 → `unpdf` 提取文本层。

**局限**:
- `searchKnowledge` 只索引文件名，PDF 正文中的关键词**不可搜索**
- 即使 PDF 能下载解析，搜索命中靠的是笔记通道，而非 PDF 本身
- 扫描件 PDF 无文本层，提取失败（需 OCR 兜底）
- 大文件（>100MB）直接跳过

### 5.2 笔记高亮直接引用（已实现）

笔记搜索返回命中处高亮原文（`highlight`），可直接作引用。

**局限**:
- 高亮内容来自笔记正文，仍是二次汇总
- 高亮片段较短，可能丢失上下文
- 笔记间的交叉引用无法体现

### 5.3 双通道合并（已实现）

`searchKnowledgeMerged` 逐词拆分 + 双通道查询 + 合并去重。

**局限**:
- wiki 通道仅匹配标题，命中率低
- note 通道虽全文索引，但索引的是笔记内容
- 合并策略无法弥补信息源的根本缺陷

为验证方案 D 的实际可行性,对 IMA 知识库中全部 25 本 PDF 书籍(84 个 PDF 中的书籍部分)进行了逐一下载提取测试。

## 6. 解决方案讨论

### 方案 A: 增强 PDF 可搜索性（推荐探索）

**思路**: 绕过 IMA 的笔记索引限制，建立 PDF 正文的本地搜索索引。

```
离线预处理流程:
  IMA 知识库 PDF → 下载 → unpdf 提取文本 → 分章节切片 → 本地向量索引

运行时查询流程:
  用户查询 → 本地向量检索(语义匹配) → 命中 PDF 章节 → 返回原始文本片段
```

**优势**:
- 直接索引原始 PDF 内容，信息零损失
- 向量检索支持语义匹配，优于关键词匹配
- 可精确到段落/章节级别引用

**劣势**:
- 需要额外的向量数据库依赖（如 ChromaDB / FAISS）
- 首次建索引耗时较长（84 个 PDF）
- 需要定期同步更新
- 增加运维复杂度

### 方案 B: 扩展笔记覆盖范围

**思路**: 在 IMA 平台中为每个重要 PDF 创建详细笔记，确保笔记内容尽可能接近原始 PDF。

**优势**:
- 不需要额外技术栈
- 利用 IMA 平台现有的笔记搜索能力

**劣势**:
- 人工维护成本高（84 个 PDF × 定期更新）
- 笔记质量取决于编写者，难以保证一致性
- 仍然是间接信息源，无法消除二次汇总的根本问题
- **不解决信息损失问题，只是缩小损失范围**

### 方案 C: PDF 下载 + 本地全文检索

**思路**: 利用已有的 PDF 下载解析能力，在本地建立全文检索索引（如倒排索引）。

```
预处理: PDF → 文本提取 → 分词 → 倒排索引(内存/磁盘)
查询: 关键词 → 倒排索引命中 → 返回上下文片段
```

**优势**:
- 技术成熟，实现简单（可用 lunr.js / MiniSearch 等轻量库）
- 不依赖外部服务
- 直接索引原始 PDF 内容

**劣势**:
- 关键词匹配，不支持语义检索
- 中文分词质量影响召回率
- 内存占用（84 个 PDF 全文索引）

### 方案 D: 混合方案（推荐）

**思路**: 保留现有双通道架构，新增**PDF 原文通道**作为第三路补充。

```
现有:
  通道 A: searchKnowledge (名称匹配)
  通道 B: searchNote (笔记正文)

新增:
  通道 C: searchPdfContent (PDF 原文检索)
    - 数据源: warm-kb-cache 预热的 PDF 文本缓存
    - 检索方式: 本地全文检索(倒排索引)
    - 命中: 返回 PDF 原文片段(非笔记摘要)
```

**合并策略调整**:
```
note 优先 → PDF 原文补充 → wiki 名称补充
(PDF 原文的信息可信度高于笔记,应优先于 wiki,但笔记有高亮优势排最前)
```

**实施路径**:
1. 复用 `warm-kb-cache` 已下载的 PDF 文本缓存
2. 新增 PDF 全文检索模块（lunr.js 或类似轻量方案）
3. 修改 `extractExcerpts` 支持 PDF 原文通道
4. 调整合并优先级：note 高亮 > PDF 原文 > 笔记正文 > wiki 标题

### 方案 E: 利用 IMA 内部 RAG 能力（长期关注）

**思路**: IMA 平台内部已实现 PDF 全文语义搜索 + 页码定位 + 图片引用。如果 IMA 未来通过 OpenAPI 暴露这些能力，将从根本上解决问题。

**证据**:
- IMA 客户端支持"点击引用编号跳转到 PDF 原文对应段落"
- IMA 客户端支持"自动标注引用出处，方便用户追溯原文片段"
- IMA 2.0 引入了 Agent 能力的"任务模式"，支持跨文档引用
- IMA 的 RAG Pipeline 已实现 Sentence-BERT 向量化 + CLIP 图片编码

**现状**: 这些能力仅在客户端/UI 层面可用，OpenAPI 尚未暴露。

**建议**: 持续关注 IMA OpenAPI 更新，推动腾讯开放 PDF 结构化查询接口。

### 方案 F: 自建多模态 RAG（终极方案）

**思路**: 完全绕过 IMA 的 API 限制，自建 PDF 多模态解析 + 向量检索系统。

```
离线处理:
  PDF → 版面分析(YOLO) → 文本提取 + 图表提取 + 图片提取
    → 语义切片(512-1024 tokens) → 向量化(Sentence-BERT + CLIP)
    → 存储(ChromaDB/Milvus) + 元数据(页码/章节/图片位置)

运行时:
  用户查询 → 混合检索(向量+关键词) → 命中段落(含页码/章节/图片)
    → 返回: 原文文本 + 页码 + 配图 URL + 章节位置
```

**优势**:
- 完全复制 IMA 内部的 RAG 能力
- 支持图片引用（CLIP 编码 → 图文匹配）
- 支持页码/章节级定位
- 信息零损失

**劣势**:
- 实现复杂度最高
- 需要 GPU 用于 CLIP/OCR 推理
- 维护成本高

## 7. 信息质量链路分析

### 7.1 当前系统(仅笔记通道)

```
原始 PDF 书籍 (100% 信息)
    ↓ IMA 平台 AI 汇总
IMA 笔记 (~30% 信息,有选择性损失)
    ↓ searchNote 索引
笔记搜索命中 (~20% 上下文,高亮截断)
    ↓ extractRelevantSnippet 摘取
引用片段 (~5% 原书内容)
    ↓ Agent 生成建议
处置建议 (基于 5% 原书内容 + AI 推理)
```

**信息损失倍率**: 原始 100% → 最终引用约 5%,损失 95%

### 7.2 方案 D 理论假设 vs 实测

方案 D 假设:

```
原始 PDF 书籍 (100% 信息)
    ↓ unpdf 文本提取
PDF 全文缓存 (~95% 信息,仅损失图表/公式)  ← 假设:提取成功率 ~95%
    ↓ 本地全文检索
命中上下文 (~30% 相关段落)
    ↓ extractRelevantSnippet 摘取
引用片段 (~10% 原书内容,但是原始表述)
    ↓ Agent 生成建议
处置建议 (基于 10% 原书原始内容 + AI 推理)
```

**实测修正**:§5.4 实测数据显示,25 本书提取成功率仅 40%,且失败的 60% 恰好是病害/鲈鱼/用药内容。修正后的链路:

```
原始 PDF 书籍 (100% 信息)
    ↓ unpdf 文本提取
    ├─ 40% 可提取(营养/饲料/行为为主) → ~95% 信息
    └─ 60% 不可提取(病害/鲈鱼/用药/大文件) → 0% 信息
         ↓
实际可用语料: 约 327 万字,但病害症状词仅 ~39 次命中
    ↓ 本地全文检索
通道 C 查询(symptoms + 疾病/治疗/用药 + 鲈鱼) → 几乎无命中
    ↓
引用片段: 以饲料/营养段落为主,病害内容仍为索引盲区
```

**结论**:方案 D 的理论收益(~10% 原始内容)建立在"PDF 全部可提取"的假设上。实测显示,在病害相关语料上提取成功率仅 40%,通道 C 的检索查询词在可索引语料中几乎无命中。方案 D 是在错误的语料上,用更快的速度检索。

### 7.3 瓶颈定位

```
信息瓶颈: 可读性 > 检索方式

当前瓶颈:
  12 本扫描件(2,572 页) → 无法提取文本 → 病害内容不可读
  3 本超限(>100MB)      → 直接跳过     → 核心病害书不可读
         ↓
结果: 327 万字可索引语料中,病害症状词仅 ~39 次
  → 无论用什么检索方式(倒排索引/substring/向量),都检索不到不存在的内容
```

## 8. 建议与下一步

### P0:语料修复(方案 D 的硬性前置)

1. **OCR 12 本扫描件(2,572 页)**
   - 成本:CPU 上 Tesseract/PaddleOCR 一次性批处理,约 1-2 小时
   - 收益:直接解锁全部病害/鲈鱼/用药内容
   - 方式:离线 OCR → 覆写 `cache/pdf/{mediaId}.txt` → warm-kb-cache 检测到变化自动重建索引

2. **处理 3 本超限书(>100MB)**
   - 成本:提高 `MAX_PDF_BYTES` 上限,或流式分片解析
   - 收益:解锁《鱼类病毒和细菌 病理学与防控》(113.9MB)、《循环水产养殖系统》(139.6MB)、《膨化饲料配制》(153.2MB)
   - 注意:超限标记有 `isStaleOversizeMark` 过期检测机制,提高上限后自动重新评估

3. **修复缓存目录 CWD 漂移问题**
   - 成本:将 `AQUASENSE_CACHE_DIR` 默认值从 `./cache`(相对路径)改为绝对路径(如 `~/.dsh/cache/`)
   - 收益:避免不同启动方式(systemd/手工/cron)各建一份缓存,索引与缓存不一致
   - 关联:方案 D 的 `pdfFiles.length !== meta.pdfCount` 告警就是撞这个问题

### P1:轻量验证(验证 PDF 通道价值)

4. **缓存上做本地检索(原短期 #2)**
   - 成本:几十行代码,在 `cache/pdf/*.txt` 上做 substring 扫描
   - 收益:立刻验证 PDF 原文通道是否真的比笔记通道引用得更好
   - 前置:P0 完成后(否则病害内容仍在盲区)

### P2:完整索引(P0 完成后)

5. **方案 D 完整版(倒排索引 + 页码/章节)**
   - 成本:~350 行 + 索引构建 + staleness 维护
   - 前置:P0 完成(语料可读率从 40% 提升到 ~90%+)、P1 验证 PDF 通道有价值
   - 价值:页码定位、章节定位在语料可读率上来之后才真正有意义

6. **信息源标注**:三段式输出中标注每条引用的实际来源(PDF 原文 / 笔记 / 笔记高亮)

### 长期(持续关注)

7. **关注 IMA OpenAPI 更新**:IMA 内部已具备 PDF 语义搜索+页码定位+图片引用能力,推动腾讯开放这些接口
8. **自建鱼类知识图谱**:将 PDF 书籍结构化为知识图谱,支持精确的实体-关系查询

### 排序逻辑

```
语料修复(P0) → 轻量验证(P1) → 完整索引(P2)
      ↓              ↓              ↓
  解锁病害内容   验证通道价值   页码/章节定位
   (必要条件)    (决策依据)     (锦上添花)
```

**核心原则**:先修复内容可读性,再优化检索架构。在 327 万字无关语料上做快速检索,不如先让病害内容变得可读。

## 9. 结论

### 9.1 核心发现

实测验证了两个事实:

1. **PDF 文字提取技术上可行**:unpdf 能正确提取有文本层的 PDF 中文内容,无乱码
2. **但最关键的语料恰好不可读**:25 本书中 60% 不可索引,且失败的 60% 恰好是病害/鲈鱼/用药内容——aquasense_advice 真正需要引用的东西

### 9.2 文档自相矛盾

本文档 §5.1 已承认「扫描件 PDF 无文本层,提取失败(需 OCR 兜底)」和「大文件(>100MB)直接跳过」,但 §7 做收益推演时将「PDF 全文缓存 ~95% 信息」当成既成事实。实测书籍提取成功率仅 40%,病害相关文档失败率高达 60%。两处自相矛盾。

### 9.3 正确的推进顺序

```
P0 语料修复(前置条件)
  ├─ OCR 12 本扫描件(2,572 页,CPU 一次性批处理)
  ├─ 处理 3 本超限书(>100MB)
  └─ 修复缓存目录 CWD 漂移
      ↓
P1 轻量验证(决策依据)
  └─ 缓存上做 substring 检索(几十行代码)
      ↓
P2 完整索引(锦上添花)
  └─ 方案 D 倒排索引 + 页码/章节
```

**核心原则**:先修复内容可读性,再优化检索架构。方案 D 的检索架构是合理的长期方向,但对"PDF 书籍检索"这个具体目标,当下最优解是先把 2,572 页扫描件 OCR 出来、把那 3 本超限书解开。在此之前,通道 C 只是在 327 万字无关语料上做快速检索——而病害知识仍然读不到。

信息质量是水产养殖 AI 诊断系统的核心竞争力。从笔记摘要到原始文献的跨越,是提升系统可信度的关键一步——而第一步是让原始文献变得可读。
